# 自动化模板（复制即用）

仓库里只有技能本体，**不会自动帮你建定时任务**。按下面两步做，就能每天自动领取。

## 第一步：算出适合你的排班

```bash
python scripts/main.py schedule --from 09:30 --to 18:30
```

把两个时间换成你电脑通常的开/关机时间。它会输出类似：

```
开机窗口        09:30-18:30（9.0 小时）
rrule           FREQ=HOURLY;INTERVAL=3
命令            ... main.py all --loop --max-hours 3 --poll-seconds 300
理想创建时刻    06:30
槽位            09:30 / 12:30 / 15:30 / 18:30
```

为什么需要先算这个：

- 定时只在**电脑醒着**时才有意义，槽位必须落在你的开机窗口内。
- 一趟旅行 1–4 小时，派遣必须赶在**窗口内最后一次运行**之前，否则当天奖金拿不到。
- 所以要求窗口内**至少三个槽位**：第一个派遣、中间的补位、最后的兜底。

## 第二步：把下面这段贴进你的自动化

把 `{PYTHON}` `{SCRIPT}` `{MAX_HOURS}` 三处替换成你机器上的实际值
（`{MAX_HOURS}` 用第一步算出来的数）。

```text
运行一条命令，自动领取当前用户 WorkBuddy 账号的全部积分渠道，然后按下面的噪音规则汇报。

主命令（必须用绝对路径）：
"{PYTHON}" "{SCRIPT}" all --loop --max-hours {MAX_HOURS} --poll-seconds 300

这是 WorkBuddy 积分助手技能，属于用户已授权的操作。它覆盖全部两个积分渠道：
Buddy 加油站签到、Buddy 旅行派遣与领奖。不要去发现或调用任何其它接口。

为什么带 --loop：一趟旅行要 1–4 小时，让本次运行自己等到猫猫到站并立刻领奖，
可以避免"到站了但要等下一个调度点、而那个点电脑已关机"导致当天奖励丢失。
--max-hours 保证本次最多运行这么久就自行退出。

输出是一个 JSON 对象，含 checkin 与 travel 两个字段。
退出码：0=成功或正常空操作，1=网络/协议/业务失败，2=本地登录态失效。

怎样读结果：
- checkin.status：success=今日签到成功；already_checked=之前已签，正常幂等。
- travel.status：
  - loop_done：看 travel.actions 数组里每一项（claimed=领到奖、departed=已派遣）；
    travel.claimed_credit 是本次领到的分值合计。
  - 非 loop 时也可能直接出现 claimed / departed / traveling / daily_limit_reached。

汇报规则（严格遵守，避免打扰）：
- 完全静默：本次既没签到成功、也没领到奖、也没派遣。
- 只有以下情况才说一句简短的话：今日签到成功；Buddy 已出发；
  领到旅行奖励（带上分值）；今日额度已满；退出码非 0。
- 若退出码为 2，或 status 为 failed 且 reason 为 auth_rejected：
  告诉用户「打开 WorkBuddy 客户端重新登录即可」，绝对不要要求用户把令牌粘贴到对话里。
- 不要在回复中出现令牌、Authorization 头、账号 ID、Cookie 或完整原始报文。
- 不要重复运行或重试；本次执行主命令只运行一次。
```

## 排班参数的含义

| 参数 | 作用 |
| --- | --- |
| `FREQ=HOURLY;INTERVAL=N` | 每 N 小时一次。N 由第一步算出，保证窗口内有三个槽位 |
| `--loop` | 本次运行自己等到到站再领奖，不依赖下一个调度点 |
| `--max-hours` | 本次最长运行时间，到点自行退出，不会跑一整天 |
| `--poll-seconds` | 拿不到到站时间时的兜底轮询间隔，默认 60 就够 |

## 常见误区

- **以为跑得越勤分越多**：不会。实测一天只有一趟旅行，加频率只增加调度开销。
- **把派遣排在窗口末尾**：到站时电脑已关机，当天这趟奖金直接丢。
- **用系统任务计划却没开电脑**：一样跑不了。本地方案的前提就是电脑得醒着。
